# Messages Module Bug Analysis

Covers server (`server/src/modules/messages/`) and client (`client/src/modules/messages/`).

---

## CRITICAL BUGS

### 1. Message Pagination Cursor Breaks If Message Is Deleted Between Pages

**File:** `server/src/modules/messages/messages.repository.ts:11-28`

```typescript
const messages = await prisma.message.findMany({
  take: limit + 1,
  cursor: cursor ? { id: cursor } : undefined,
  skip: cursor ? 1 : 0,
  // ...
});
```

The cursor-based pagination uses `skip: 1` to skip the cursor record itself. If the cursor-referenced message was **soft-deleted** (has `deletedAt` set) by another user between page fetches, Prisma still finds the record (soft-delete just sets a field, doesn't remove it). This works — the query succeeds.

**However**, if the cursor message is **hard-deleted** (if a future cleanup job removes soft-deleted messages), or if the cursor references a message from a different conversation (an attacker crafts a malicious cursor), Prisma throws a `Cursor not found` error. This propagates as an unhandled 500.

**Worse:** The cursor is a UUID generated by the client from the previous page's `nextCursor`. If the client stores this cursor and the server restarts (in-memory state lost) or the message is deleted in another session, pagination breaks mid-scroll. The user sees a generic error and cannot load older messages.

### 2. Optimistic Message Adds Non-Existent `messages` Field to Conversation Type

**File:** `client/src/modules/messages/hooks/useMessages.ts:82-92`

```typescript
queryClient.setQueryData(queryKeys.conversationMessages(conversationId), ...);
// Also sets on the conversation cache:
queryClient.setQueryData(queryKeys.conversations, (old) => ({
  ...old,
  messages: [optimisticMessage as unknown as Message],  // ← BUG
}));
```

The `Conversation` type does **NOT** have a `messages` field. This line:
1. Pollutes the conversation cache with a non-existent field
2. Uses `as unknown as Message` — a double cast that hides type errors
3. When the real message arrives via socket, `handleConversationNew` writes to a different part of the cache

This `messages` key on the conversation object is never read by any component. It's dead data that wastes memory and could cause unexpected behavior if React Query serializes/deserializes the cache.

## HIGH BUGS

### 3. `editMessage` Sets `updatedAt` Client-Side Without Updating DB

**File:** `server/src/modules/messages/messages.service.ts:84`

```typescript
// In createMessageTransaction:
conversationMetadata.updatedAt = new Date();  // ← generated on server but not from DB commit
```

The `updateMessage` repository function (line 77) only updates `content` and `isEdited` — it does **NOT** update `updatedAt` on the conversation. But the socket dispatcher emits `conversationMetadata.updatedAt` as `new Date()` to all clients. This means:
- All clients see a newer `updatedAt` that doesn't match any database column
- The sorting order in the sidebar uses this synthetic timestamp
- If the DB clock and server clock differ, the sort order is inconsistent

### 4. Socket Event Sends Raw Prisma `Message` Not `MessageDTO`

**File:** `server/src/socket/socket.dispatcher.ts:51`

```typescript
io.to(`conversation:${conversationId}`).emit(SOCKET_EVENTS.MESSAGE_NEW, {
  message,  // ← raw Prisma model, not a DTO
  conversationMetadata,
});
```

The dispatcher emits the raw Prisma `Message` object. This may contain:
- Fields the client doesn't expect (e.g., `replyToId` when the type doesn't have it)
- Relations included/excluded differently than the client `Message` type
- Prisma-specific metadata or hidden fields

The client `Message` type in `client/src/modules/chat/types/socket.ts` may not match the Prisma model. If a Prisma field is renamed or added, the client silently drops it or crashes trying to access it.

### 5. Promise Chain in `message.handler.ts` Detached — Errors Silently Swallowed

**File:** `server/src/socket/handlers/message.handler.ts:88-128`

```typescript
findById(payload.conversationId).then(async (conv) => {
  const pushPromises = conv.members
    .filter(m => m.userId !== userId && ...)
    .map(m => sendPushNotification(m.userId, { ... }));
  Promise.all(pushPromises).catch(e => console.error("[Push] Error:", e));
}).catch(e => console.error("[Push] Error fetching conversation:", e));

return callback?.({ success: true, data: message });
```

The entire `findById` → push notification chain is **not awaited**. The callback at line 130 fires immediately. If the socket disconnects before the push promises settle:
- Errors are only caught by inner `.catch()` handlers
- The main try-catch on line 134 does NOT cover this code path
- Push notifications are silently dropped with no retry
- The caller has no visibility into whether push notifications succeeded

### 6. Socket Rate Limiter Silent Message Loss Without Ack Callback

**File:** `server/src/socket/middlewares/rateLimiter.ts:22-32`

```typescript
if (current.count >= max) {
  if (next) {
    next(new Error("sending too quickly"));
  }
  return;
}
```

If the client sends a fire-and-forget emit (no ack callback), the rate-limited message is **silently dropped** with zero feedback:
- `next` is `undefined` → no error passed to the callback
- The function returns without calling `next(data)` → the handler never executes
- The client never knows the message was rejected
- The user sees the optimistic message in the UI but it never arrives at the server

### 7. Document Title Only Shows `(1)` Regardless of Actual Unread Count

**File:** `client/src/socket/handlers/message.handlers.ts:82-83`

```typescript
const originalTitle = document.title.replace(/^\(\d+\)\s/, "");
document.title = `(1) New Message! - ${originalTitle}`;
```

Every new message sets the count to `(1)` regardless of how many unread messages exist. If 5 messages arrive while the user is away, the title still shows `(1)`. The regex only strips one occurrence of the prefix, so rapid messages create nested prefixes: `(1) New Message! - (1) New Message! - Original Title`.

### 8. `handleMessageNew` Iterates Workspace-Channel Queries Twice

**File:** `client/src/socket/handlers/message.handlers.ts:33-44,48-67`

```typescript
// First pass: update workspace-channel caches (lines 33-44)
// Second pass: query the same caches AGAIN to update workspace unread totals (lines 48-67)
```

Lines 33-44 update individual channel caches with the new message. Lines 48-67 query the **same caches** again to recalculate workspace unread totals. The `break` on line 64 only breaks the inner `for` loop, not the outer `for...of`, so after finding the matching channel, it continues iterating other channel queries unnecessarily. This doubles the processing time for every incoming message in a workspace channel.

## MEDIUM BUGS

### 1. Cursor Pagination Fails Silently on Invalid Cursor

**File:** `server/src/modules/messages/messages.repository.ts:6-29`

```typescript
cursor: cursor ? { id: cursor } : undefined,
```

If an invalid/ non-existent cursor UUID is provided, Prisma throws `NotFoundError` which propagates up as a 500. The `getMessages` controller catches this as a generic error:
```typescript
console.error("Error fetching messages:", error);
res.status(500).json({ error: "Internal server error" });
```

The user gets a generic 500 when they provide a bad cursor. The `notifications.repository.ts` has the same issue — no cursor existence check.

### 2. Message Socket Emissions Are Fire-and-Forget After Response

**File:** `server/src/modules/messages/messages.controller.ts:32-36`

```typescript
try {
  dispatchMessageEvent("NEW", conversationId, message, conversationMetadata);
} catch (err) {
  console.error("[Socket.io] Failed to emit message:new from HTTP endpoint", err);
}
```

The socket event is dispatched after the DB write but before the HTTP response is sent. If socket emission fails:
- The message is saved to DB (correct)
- The HTTP response is still sent with 201 (correct)
- But real-time clients don't receive the update (silent failure)

This is consistent across all message operations (create, update, delete). The error is logged but there's no retry mechanism, no fallback to polling, and no monitoring alert.

### 3. `deleteMessage` Doesn't Verify Message Belongs to Conversation

**File:** `server/src/modules/messages/messages.service.ts:102-144`

The `deleteMessage` function only checks `message.userId !== userId` for authorization but never verifies the message belongs to the conversation in the URL params (`conversationId`). The route params include both `conversationId` and `messageId` but the service only uses `messageId`.

If someone calls `DELETE /conversations/{convA}/messages/{msgInConvB}` with a valid messageId from a different conversation, the deletion succeeds (assuming they own the message). The `requireConversationMember` middleware checks access to `convA`, not the message's actual conversation. This is a **cross-conversation deletion vulnerability**.

Same issue exists in `editMessage` — it doesn't validate `message.conversationId` matches the route `conversationId`.

### 4. `editMessage` Updates `updatedAt` on Conversation Even When Not Latest Message

**File:** `server/src/modules/messages/messages.repository.ts:91-110`

The `updateMessage` function only updates the message content — it does NOT update the conversation's `updatedAt`. This is correct behavior (editing an old message shouldn't bump the conversation).

However, `createMessageTransaction` in the same file (line 68-73) DOES update `updatedAt` on the conversation via `conversation.update`. The `dispatchMessageEvent` in the controller always emits `conversationMetadata` for NEW messages but conditionally emits it for UPDATE/DELETE (based on whether the message was the latest). This inconsistency means:
- Editing the latest message → `conversationMetadata` is emitted with `updatedAt: new Date()` (a new Date, not the actual DB value)
- Editing an old message → no `conversationMetadata` emitted at all

The client-side conversation sorting does get an `updatedAt` bump when the latest message is edited, but it's generated on the server via `new Date()` rather than from the actual DB commit time. Under high load, this clock value may differ from the DB value.

## MINOR BUGS

### 5. No Message Content Sanitization

**File:** `server/src/modules/messages/messages.service.ts:22-59`

Message `content` is stored as-is with no sanitization. While React handles XSS in rendering, the raw content is served in API responses. If the API is consumed by a non-React client (mobile app, API integration), the unsanitized content could contain malicious HTML/JS.

The `content.trim()` in `updateMessage` (repository line 98) is minimal sanitization.

### 6. `deleteMessage` Returns Updated Conversation Metadata Even on Non-Latest Deletion

**File:** `server/src/modules/messages/messages.service.ts:116-143`

The function creates `conversationMetadata` only when `conversation?.latestMessageId === messageId` (line 132). But the `conversationMetadata` variable is initialized as `null` and only set inside the if-block. The return value (line 143) correctly returns null metadata for non-latest deletions. However, the `dispatchMessageEvent` in the controller passes this to socket, which does nothing with `null` metadata. This is correct but confusing — a cleaner pattern would be to return `null` explicitly.

### 7. Rate Limiter Applied to Edit/Delete But Not Create

**File:** `server/src/modules/messages/messages.routes.ts:20-27`

The `messageLimiter` is applied to POST (create), PATCH (update), and DELETE routes. But the rate limiter is applied **before** `authMiddleware`. If the rate limiter returns an error before auth runs, the response doesn't include auth context. The ordering should be: `authMiddleware → messageLimiter → validate → requireConversationMember → controller`.

Actually, looking more carefully at the route:
```typescript
router.post("/", messageLimiter, authMiddleware, ...);
```

The `messageLimiter` runs BEFORE `authMiddleware`. This means:
- If the rate limiter blocks the request, unauthenticated users can't distinguish between "rate limited" and "not authenticated"
- The rate limiter works on IP, not userId (since auth hasn't run yet)

This is intentional but worth noting — the rate limiter key is IP-based for unauthenticated requests and userId-based only if the middleware order is swapped.

### 8. `getMessages` Returns `nextCursor` Even When Page Is Empty

**File:** `server/src/modules/messages/messages.service.ts:5-20`

If the conversation has no messages, `messages` is an empty array, `hasNextPage` is `false`, and `nextCursor` is `null`. The response is:
```json
{ "data": [], "nextCursor": null }
```

This is correct but the client must handle `null` vs empty array pagination. Some cursor implementations use `undefined` to indicate "no more pages" vs `null` for "initial page not loaded yet."

### 9. `editMessage` Allows Editing Deleted Messages After Check Removed

**File:** `server/src/modules/messages/messages.service.ts:65-99`

The function explicitly checks `if (message.deletedAt)` and throws `"Cannot edit a deleted message."` — but only on line 70. If this check is ever removed, users could edit deleted messages and "un-delete" them by providing new content (since the soft-delete only sets `deletedAt`, not the content).

### 10. Import at Bottom of File

**File:** `server/src/modules/messages/messages.service.ts:146`

```typescript
import { runTransaction as prismaTransaction } from "@/lib/transaction.js";
```

This import is at the **bottom** of the file. ES module imports are hoisted so it works, but this violates the convention of imports at the top. Code reviewers may miss this import, and tooling may not auto-organize it correctly.

### 11. Socket `MESSAGE_SEND` Callback Races With Optimistic Update

**File:** `client/src/modules/messages/hooks/useMessages.ts:29-43`

```typescript
socket.emit("message:send", payload, (response: any) => {
  if (response?.error) {
    // show error
  }
});
```

The socket callback fires asynchronously. The `onMutate` handler has already optimistically added the message to the cache. If the server responds with an error:
- The optimistic message is already visible in the UI
- The error callback may not remove it (depends on implementation)
- The user sees a message that was never actually saved

Conversely, if the callback fires before `onMutate` completes (possible under heavy load), the message isn't in the cache yet when the success response arrives — leading to a duplicate or missing message.

### 12. `countUnreadMessages` Double-Filters on Author — Confusing Logic

**File:** `server/src/modules/conversations/conversations.repository.ts:163-180`

```typescript
const whereClause = {
  conversationId,
  userId: { not: userId },  // ← excludes messages by the current user
};
```

The repository already filters out the user's own messages. But the service layer also filters:
```typescript
conv.latestMessage?.userId !== userId  // in conversations.service.ts:22
```

This means:
- The service has a fast path: if the latest message is the user's own, skip unread count entirely
- But if there are older unread messages from other users, they're never counted
- The two conditions overlap confusingly: the repo filter is redundant when the service fast-path is active

**Scenario:** Alice sends messages 1, 2, 3. Bob reads #1. Alice sends #4 (latest). Bob's unread count = 0, but messages #2 and #3 are unread. The service fast-path (`hasUnread = false`) prevents them from being counted.

### 13. `getMessages` Returns Raw Prisma Model With All Relations

**File:** `server/src/modules/messages/messages.repository.ts:6-29`

The `getMessages` query includes the `user` relation:
```typescript
include: {
  user: { select: { id: true, username: true, avatarPath: true, fullName: true } },
  replyTo: { include: { user: { select: { id: true, username: true } } } },
}
```

This returns full user objects for every message. On a conversation with 500 messages, this is ~500 user objects serialized in the response. This is wasteful — the user data is the same for consecutive messages by the same author. Consider batching or caching.
